# Что означает ответ NDI

В письме сотрудник NDI говорит не о технической невозможности и не об отказе. Он пишет, что **у него самого нет внутреннего разрешения активировать API для компании**, поэтому вопрос передан коллегам в NDI Norway. То есть текущий статус:

> **официальный API запрошен, заявка эскалирована, решение ожидается.**

Это положительный сигнал, но **доступа пока нет**. До получения документации, ключей и тестового ответа нельзя считать официальный API доступным и строить сроки вокруг предположения, что он точно заработает. 

## Как теперь правильно расставить приоритеты

1. **Официальный NDI API** — основной желательный вариант для актуальной цены, остатка, склада, срока поставки, резервирования и создания заказа, если эти методы там вообще имеются.
2. **CSV/файловая выгрузка NDI** — основа локального каталога и массовой синхронизации.
3. **Официальный Statens vegvesen API** — поиск автомобиля по регистрационному номеру и получение разрешённых комбинаций шин и дисков.
4. **Внутренние запросы кабинета NDI** — только временный или резервный вариант после проверки условий использования.
5. **Playwright/headless-автоматизация кабинета** — самый последний вариант, отдельный по стоимости и поддержке.

Твой первоначальный подход с внутренними запросами был технически нормальным для ситуации, когда других данных не было. Но после появления CSV и движения по официальному API уже не стоит делать внутренний кабинет основой магазина.

## Отдельно про поиск автомобиля

Поиск по номеру вообще лучше не привязывать к NDI. У Statens vegvesen есть официальный REST API, который позволяет искать автомобиль по регистрационному номеру или VIN и возвращает технические данные, включая утверждённые комбинации шин и дисков. Ключ может получить норвежская компания через электронную идентификацию; для API без сведений о владельце указан лимит до 50 000 вызовов в сутки на ключ. ([Statens vegvesen][2])

Это серьёзно упрощает проект:

* NDI отвечает за товары, цены, остатки и поставку.
* Statens vegvesen отвечает за автомобиль и разрешённые размеры.
* EasyTire не зависит от одного поставщика сразу по всем направлениям.

Нюанс: для **точного подбора дисков** одного размера недостаточно. Кроме диаметра и ширины могут понадобиться PCD, ET, DIA, нагрузка, крепёж и другие параметры. Поэтому после получения примера ответа Statens vegvesen надо проверить, хватает ли его полей или NDI предоставляет дополнительную таблицу совместимости.

# Как сохранить высокую скорость

Твой пример с крупным магазином здесь действительно релевантен. Схема будет быстрой при соблюдении нескольких правил.

### 1. Не обращаться в NDI при каждом открытии страницы

Каталог, цена, остаток и сроки синхронизируются в локальную базу. Посетитель работает с локальными данными, а не ждёт ответ NDI.

### 2. Не хранить тяжёлые фильтры в стандартном WordPress `postmeta`

Ширина, профиль, диаметр, сезон, бренд, тип, цена и склад должны находиться в нормализованных таблицах Laravel с индексами.

При каталоге около 50 тысяч товаров обычного MySQL с правильными составными индексами и Redis вполне достаточно. Meilisearch или Elasticsearch на первом этапе не нужны — это лишняя инфраструктура, пока нагрузка не доказала обратное.

### 3. Использовать CSV для массовых данных, API — для оперативных

Оптимальная схема:

* CSV обновляет весь каталог по расписанию.
* NDI API проверяет цену, остаток и срок перед заказом.
* Если API предоставляет изменения или дельту, она обновляет данные между полными CSV-импортами.
* В интерфейсе хранится время последней успешной синхронизации.

### 4. Не удалять товары сразу

Если позиция исчезла из очередного CSV, её лучше сначала помечать отсутствующей или архивной. Иначе временно неполный файл поставщика может удалить половину каталога.

### 5. Все операции должны быть повторяемыми

Импорт, платёжные вебхуки, создание записи в Notion и Telegram-уведомления должны быть идемпотентными: повторный вызов не создаёт второй заказ.

# Важный момент с оплатой

Формулировка из первоначального ответа «перед оплатой ещё раз проверяем цену и остаток» правильная, но она не решает проблему полностью.

Между проверкой и завершением платежа товар могут купить. Поэтому надо выяснить, что умеет официальный NDI API:

* только возвращать остаток;
* резервировать товар;
* создавать предварительный заказ;
* создавать окончательный заказ;
* отменять резерв;
* возвращать статус заказа.

Лучший поток:

1. Проверить цену и остаток.
2. Зарезервировать товар в NDI.
3. Авторизовать или принять платёж.
4. Подтвердить заказ.
5. Создать локальную запись.
6. Поставить в очередь Notion и Telegram.

Если резервирования в NDI нет, заказчик должен понимать риск изменения остатка во время оплаты. Это надо явно описать в логике возвратов и ручной обработки.

# Сообщение, которое сейчас стоит отправить заказчику

```text
Максим, перед началом хочу письменно зафиксировать архитектуру, чтобы дальше не возникло разночтений.

В первом сообщении я указал Laravel и отдельный API-слой, но подробно не расписал разделение системы. Сам сайт, страницы услуг, SEO, корзину, оплату и удобную административную часть предлагаю реализовать на WordPress + WooCommerce.

Всю тяжёлую и нестандартную логику выносим в отдельный сервис на Laravel: импорт CSV NDI, официальный API, поиск и совместимость, цены, остатки, склады, сроки доставки, кеширование, очереди, логи и финальную проверку товара перед оплатой.

То есть это не обычная сборка магазина на WooCommerce. WordPress будет отвечать за быструю витрину и управление сайтом, а Laravel — за каталог и интеграции. Такой подход я уже использую на магазине с большим каталогом, поэтому тяжёлые данные и фильтры не будут работать через стандартную базу WordPress.

По ответу NDI официальный API пока не отклонён, но ещё не активирован: вопрос передан коллегам в NDI Norway. Поэтому начинаем со структуры, CSV-интеграции и собственного адаптера. После получения документации официальный API подключится без переделки сайта.

Поиск автомобиля по номеру отдельно предлагаю реализовать через официальный API Statens vegvesen, а NDI использовать для товаров, цен, остатков и заказов. Это уменьшит зависимость магазина от одного внешнего сервиса.

Для старта нужны пример CSV, доступ к кабинету NDI и имеющимся запросам, материалы сайта, формы, структура Notion и выбранная платёжная система.

Подтвердите, пожалуйста, что фиксируем именно такое разделение, и я начинаю с интеграционного контура и импорта данных.
```

## С чего реально начинать работу

Не с вёрстки.

Первый технический результат должен состоять из:

1. Двух отдельных проектов и тестового окружения: WordPress и Laravel.
2. Зафиксированного API-контракта между ними.
3. Импортера тестового CSV NDI с журналом ошибок.
4. Прототипа поиска автомобиля по регистрационному номеру.
5. Нормализованной схемы шин, дисков, размеров, цен, складов и остатков.
6. Отчёта о том, какие операции реально поддерживает NDI API.
7. Письменной границы текущего Safe.

**Итоговая оценка:** архитектура нормальная, профессиональная и уже подтверждена твоим опытом на большом каталоге. Основная опасность сейчас не WordPress и не скорость, а размытый объём за 44 879 грн и отсутствие явного согласования, что WordPress будет витриной, а Laravel — отдельным ядром. Это надо закрыть сообщением выше до первого коммита.
