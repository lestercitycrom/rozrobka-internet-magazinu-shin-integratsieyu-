# EasyTire — стратегия тестирования

Статус: принят, применяется с первого инкремента  
Дата: 2026-07-31  
Ответственный: Mister Black (QA/автоматизация)

## Цель и границы

Стратегия задаёт проверяемое качество с первого инкремента для модульного Laravel-монолита, предложенного в `ADR-001`. Она исходит из фактической схемы данных:

```text
NDI Excel/CSV/SFTP -> локальный каталог -> NDI Inquiry перед оплатой -> NDI Order
Statens vegvesen -> автомобиль и разрешённые размеры
Laravel -> payment / Notion / Telegram через адаптеры и очереди
```

Архитектура подтверждена: единый модульный Laravel-монолит, собственная административная панель без готовых admin-panel frameworks. Правила ниже применяются ко всему приложению.

Качество важнее номинального количества тестов. Автотест должен проверять правило, отказ или наблюдаемый результат, а не детали реализации. Тестовые данные синтетические либо явно предоставленные NDI для теста. Ни один тест не содержит реальных credentials, номеров карт, регистрационных номеров клиентов или боевых заказов.

## Риски, которые определяют приоритет

| Риск | Последствие | Обязательная защита |
|---|---|---|
| Суточный импорт NDI устарел | неверная цена, остаток или срок | проверка Inquiry непосредственно перед оплатой; видимый отказ при расхождении |
| В NDI не подтверждены резерв/отмена | списание при уже недоступном товаре; ошибочный заказ | payment authorization/capture либо ручная политика; мутационные NDI-тесты только с письменным разрешением |
| Повтор webhook/задачи очереди | двойная оплата, два заказа, два сообщения | идемпотентные ключи, уникальные ограничения, повторные delivery-тесты |
| Неполный или изменившийся файл поставщика | исчезновение каталога, неверные цены | валидация файла, staging/import report, мягкая деактивация, rollback |
| Ошибочная совместимость авто/диска | небезопасная рекомендация и возвраты | явная граница данных, точные fixtures, отказ при неполных параметрах |
| Норвежский интерфейс или мобильный checkout непонятен | потеря заказов | E2E на `nb`, responsive-проверки и accessibility gate |

## Тестовый контур и данные

| Контур | Назначение | Внешние системы |
|---|---|---|
| Локальный/CI | быстрые unit, feature и contract tests | только fakes, HTTP fake, локальная БД/Redis |
| Ephemeral review environment | ручная приёмка и E2E ветки | sandbox платёжного провайдера; тестовые mock-сервисы |
| Staging | релизный smoke и согласованные интеграции | NDI read-only Inquiry с разрешённым SKU; sandbox платежей; тестовые Notion/Telegram endpoints |
| Production | только минимальный post-deploy smoke | без создания заказа, оплаты и внешних сообщений |

### Fixtures

Поддерживаются небольшие, читаемые фикстуры: минимум одна шина, один диск, комплект, товар без остатка, товар с изменённой ценой, товар без изображения, строки двух складов и неполная/ошибочная строка импорта. Каждая фикстура имеет стабильный внутренний SKU и ожидаемый итог нормализации.

Для автомобиля нужны: валидный ответ с разрешённым размером, авто без нужных полей, не найденный номер, ответ 429/5xx и несовместимый диск. Реальные регистрационные номера в fixtures не допускаются.

Тесты фиксируют время через clock/freeze time. Валюта, НДС, округления, zone доставки и правила наценки задаются явно в factory/fixture, а не зависят от текущей даты или production-конфигурации.

## Пирамида автоматизации

| Уровень | Инструмент/тип | Что проверяет | Когда запускается |
|---|---|---|---|
| Unit | PHPUnit/Pest | money, НДС/округление, наценка, совместимость, state machine, идемпотентность | каждый PR |
| Feature | Laravel HTTP/database/queue tests | каталог, корзина, checkout, политики, локализация, валидация, jobs | каждый PR |
| Integration | реальные Laravel adapters против local fake/sandbox | MySQL, Redis, filesystem, очередь, importer, payment webhook, Notion/Telegram adapter | каждый PR; расширенно nightly |
| Contract | schema/recorded fixtures | NDI/Statens/payment/Notion/Telegram запросы и ответы | PR при изменении адаптера; nightly |
| E2E | Playwright | критический путь покупателя и администратора в браузере | PR smoke; полный набор nightly/release |
| Manual exploratory | чек-лист | визуальные, язык, edge cases интеграций | перед релизом и по изменению UX |

Не требуется 100% coverage. Минимум: все money-, checkout-, order-state-, importer- и integration-boundary классы имеют unit/feature coverage, а все сценарии с пометкой P0 в матрице ниже автоматизированы до production. Coverage не заменяет сценарии и контрактные тесты.

## Laravel: правила по слоям

### Unit

Покрываются чистые доменные правила без HTTP, БД и сети:

- расчёт итоговой суммы: товар, количество, скидка/наценка, услуги, НДС, доставка и округление NOK;
- сравнение snapshot цены с финальным Quote; допустимое расхождение должно быть явным бизнес-правилом;
- переходы заказа: `draft -> pending_payment -> paid -> ndi_pending -> confirmed/failed/manual_review/refunded` (набор окончательных статусов уточняется при реализации);
- идемпотентный ключ для payment webhook, NDI order, Notion и Telegram;
- определение пригодности шины и диска только при полном наборе данных; неполные данные никогда не превращаются в «совместимо»;
- маппинг raw NDI строк в нормализованные DTO и классификация ошибок.

### Feature

Проверяются HTTP-границы Laravel с настоящей тестовой БД:

- публичный поиск и фильтры отдают только активные, доступные позиции и не раскрывают закупочные/NDI поля;
- корзина не доверяет цене, количеству, SKU, языку или услугам из браузера;
- checkout отклоняет просроченную/изменённую цену, отсутствующий товар, неверную доставку и невалидные данные;
- пользователь видит локализованную ошибку, а не текст внешнего API или stack trace;
- admin routes требуют аутентификации, роли и CSRF; покупатель не может читать/менять чужой заказ;
- очереди dispatch/chain и outbox создаются в транзакции с заказом;
- повторенная доставка webhook не меняет оплаченный заказ и не создаёт дубликаты;
- API возвращает согласованные коды ошибок и correlation ID без секретов.

### Integration

Запускать с MySQL и Redis, совместимыми с окружением приложения (не заменять все проверки SQLite, если продакшен использует MySQL). Проверять:

- импорт Excel/CSV в staging-таблицы, валидацию обязательных полей, статистику, транзакционную публикацию и soft-disable пропавших SKU;
- повторный импорт одинакового файла, частично испорченный файл, повтор задачи и отмену worker-а;
- cache invalidation после импорта и блокировку конкурентных импортов;
- retry/backoff/dead-letter для временных сбоев, отсутствие retry для валидационных 4xx;
- payment sandbox/webhook fake: подпись, replay, порядок событий, timeout и refund/void path;
- Notion/Telegram: outbox, повторная отправка без дубля, redaction PII в логах;
- мониторинговые события: неуспешный импорт, устаревшие данные, отказ NDI перед оплатой, неотправленный outbox.

## Контрактные тесты интеграций

Контракт — часть исходного кода адаптера: зафиксированные запросы и минимальные ответы хранятся без секретов, персональных данных и production IDs. На изменение адаптера меняется fixture и явно рассматривается diff контракта.

### NDI: безопасный протокол

1. По умолчанию CI использует NDI fake и записанные `quote_A2` fixtures: успех, `ErrorCode`, пустой остаток, timeout, XML/schema error, неправильный `PartyID` и ответ без цены.
2. Staging может выполнить один или несколько **read-only** `inquiry_A2` только при наличии согласованного NDI SKU, корректного PartyID, HTTPS endpoint и rate-limit конфигурации. Запросы сериализуются и журналируются без Basic credentials и полного тела с секретами.
3. `PlaceOrder`, статус, отмена и любая тестовая операция, меняющая состояние NDI, запрещены в CI и staging до одновременного выполнения условий: письменное разрешение NDI, специально выделенный товар/количество, подтверждённый endpoint, инструкция остановки/отмены, контакт для эскалации и одобренный тест-кейс.
4. Даже после разрешения такой тест запускается вручную с защищённым секретом и явным флагом `ALLOW_NDI_MUTATION=true`; он никогда не запускается по cron, push, PR или повторно после retry.
5. Любое неожиданное внешнее order ID — P0-инцидент: прекратить дальнейшие мутационные вызовы, сохранить redacted correlation ID и уведомить владельца интеграции.

Проверяемые поля NDI contract: namespace `http://www.reifen.net`, обязательные поля запроса, корректная классификация `ErrorCode`, SKU, available quantity, delivery date, необязательная цена, продавец/склад, замены и XML-ошибка. Нельзя считать цену полученной из Inquiry: текущий аудит подтверждает в реальном `quote_A2` количество и дату, но не цену.

### Остальные адаптеры

- Statens vegvesen: request shape, отсутствие owner data, mapping разрешённых размеров, `404`, `429`, timeout и cache TTL.
- Payment: signed webhook, сумма/валюта/merchant order ID, success/fail/cancel, повтор, события в неверном порядке, authorization/capture или documented fallback.
- Delivery: допустимые самовывоз/согласованная зона; нельзя предлагать неподтверждённую B2C-доставку NDI. Rate/label API, если появятся, тестируются через sandbox/fake до договора с перевозчиком.
- Notion/Telegram: необходимый минимум полей заказа, безопасное представление данных, 4xx/5xx и retry. Notion не используется как источник истины.

## Playwright E2E

E2E создают свои тестовые записи через seed/API и после прогона не обращаются к боевым провайдерам. Селекторы — устойчивые `data-testid` или доступные роли/labels, не CSS-позиции и не локализованный текст.

### Покупатель

- открыть каталог, отфильтровать шины, открыть карточку, добавить товар и услугу в корзину;
- пройти поиск автомобиля по безопасному fixture-ответу, получить допустимый размер и увидеть подходящие позиции;
- вручную выбрать размер без регистрации авто;
- изменить количество, удалить позицию, проверить корректную NOK-сумму и НДС;
- checkout в payment sandbox: success, cancel/fail и возврат на сайт;
- перед оплатой получить расхождение цены/остатка и увидеть безопасный отказ без списания;
- открыть оплаченный заказ только как его владелец; повторить callback и убедиться в одном заказе;
- недоступный/устаревший каталог корректно сообщает о состоянии, а не показывает «в наличии».

### Администратор

- вход с MFA/ролью, если они реализованы; неавторизованный пользователь перенаправлен на login;
- импорт валидного файла, просмотр отчёта, публикация результата и обновление каталога;
- импорт файла с ошибками: видны строки/причины, опубликованный каталог не повреждён;
- редактирование правила наценки/контента разрешено только нужной роли и фиксируется в audit log;
- заказ в `manual_review` можно обработать без повторного NDI/payment действия;
- повторить доставку Notion/Telegram из outbox без дублирования;
- админ не видит секреты, Basic auth или полные реквизиты платежа.

### Браузеры, экраны и язык

PR smoke: Chromium desktop `1440x900` и mobile `390x844`. Nightly/release: Chromium, Firefox и WebKit; desktop `1440x900`, tablet `768x1024`, mobile `390x844` и `320x568`.

Основной и пока единственный публичный язык — `nb-NO`. Русский язык поддерживается в собственной административной панели: E2E проверяет переключение `nb`/`ru`, сохранение выбранной локали, перевод навигации, форм и ошибок и отсутствие смешения языков. Публичные русскоязычные маршруты не включаются без отдельного решения заказчика.

На mobile сценарии включают меню, фильтр, карточку, корзину, checkout и формы: отсутствие горизонтального скролла, перекрытия fixed-элементов, недостижимых кнопок и потери фокуса с виртуальной клавиатурой.

## Accessibility, visual и ручной smoke

В CI запускается axe-проверка ключевых страниц: каталог, карточка, корзина, checkout, login и admin-import. Новые critical/serious нарушения блокируют PR; известные исключения имеют issue, владельца и срок.

Обязательные ручные проверки перед релизом: keyboard-only путь до оплаты, видимый focus, корректные labels/error summary, семантические heading, контраст, масштаб браузера 200%, базовая работа screen reader на checkout, изображения с осмысленным alt, language attribute (`nb`/`ru`). Автоматизация не заменяет ручную проверку реального UX.

Visual regression делается только для устойчивых компонентов: header, карточка, корзина, checkout и admin-import report. Динамические цены, даты, баннеры и изображения стабилизируются fixture-данными. Значимое изменение screenshot требует осознанного approve в PR.

После каждого deploy выполняется read-only smoke: главная, health/ready endpoint, каталог, карточка, корзина, login и один synthetic checkout до перенаправления в оплату. В production smoke не выполняет payment callback, NDI Inquiry, импорт или внешнюю доставку.

## Security и performance проверки

Security suite на каждом PR включает: authorization/policy tests, CSRF, validation, output escaping/XSS для контента и фильтров, signed payment webhook, protection against mass assignment, rate limit для поиска авто/login/checkout, безопасные ошибки, redaction secrets и PII в логах. Зависимости проверяются lockfile-аудитом; critical/high уязвимость в production-зависимости блокирует релиз до оценки и исправления/компенсирующей меры.

Перед MVP-release проводится authenticated DAST в staging по согласованному scope, без destructive payloads и без боевых интеграций. Не проводить нагрузочное тестирование NDI без их лимитов и разрешения. Нагрузочно тестировать локальный каталог, cache, очередь и checkout с NDI fake: зафиксировать целевые SLO после появления макетов и инфраструктуры; до этого не объявлять непроверенные цифры.

## CI/CD gates

| Этап | Обязательная проверка | Gate |
|---|---|---|
| Каждый PR | форматирование/static analysis, unit, feature, migration test, security suite, NDI/adapter contract tests, Chromium E2E smoke | падение любой P0-проверки блокирует merge |
| Изменение адаптера/схемы | contract fixture diff, integration suite, migration backward/forward check | нужен review владельца интеграции |
| Nightly | полный integration suite с MySQL/Redis, конкурентные jobs, полные browser matrix, axe, visual regression | создаётся issue/alert, P0 не игнорируется |
| Release candidate | full E2E, ручной smoke/a11y, sandbox payment, staging read-only NDI Inquiry при разрешении, backup/rollback rehearsal | все P0 pass; P1 приняты письменно или исправлены |
| Deploy | migration с backup/rollback plan, production read-only smoke, мониторинг ошибок/очереди | release owner подтверждает результат |

Flaky E2E не ретраятся бесконечно: допускается один диагностический повтор в CI с артефактами trace/video/screenshot; повторно нестабильный тест становится приоритетным defect и не маскируется `skip` без issue, владельца и срока. Любое изменение теста, ослабляющее P0-assertion, требует отдельного reviewer approval.

## Артефакты и наблюдаемость

CI хранит JUnit/coverage, Playwright trace/video/screenshot, redacted HTTP fixture diff, import report и логи job/correlation ID. Артефакты не должны содержать credentials, номера карт, токены, customer vehicle registration или полные адреса.

Для каждой интеграционной операции нужны correlation ID, provider operation ID (если есть), статус попытки, безопасный код ошибки и timestamp. Дашборд/alerts минимум покрывают: возраст последнего успешного импорта, число ошибок импорта, очередь/retry/dead-letter, payment webhook failures, NDI inquiry failures/latency, недоставленный outbox и заказы в manual review.

## Критерии готовности

### Готовность функции к merge

- есть acceptance criteria и тестовые данные; затронутые P0/P1 тесты добавлены или обновлены;
- бизнес-правила покрыты unit/feature на подходящем уровне;
- внешний вызов имеет timeout, error mapping, idempotency/retry policy и contract fixture;
- нет реальных секретов/PII в коде, тестах, артефактах и PR;
- PR CI зелёный, migrations проверены, reviewer одобрил изменения.

### Готовность MVP к production

- все P0 из матрицы автоматизированы и прошли на release candidate;
- импорт, checkout, payment success/fail и idempotency прошли с изолированными данными;
- NDI выполняется только в подтверждённой границе: read-only Inquiry уже проверен, а `PlaceOrder` выключен до письменного разрешения и процедуры отмены;
- утверждена политика оплаты при отсутствии NDI reservation/cancellation (authorization/capture либо manual review/refund);
- `nb-NO` пользовательский путь и заявленный `ru` путь проверены на desktop и mobile;
- нет открытых P0; все P1 исправлены либо явно приняты владельцем продукта с датой устранения;
- пройдены staging smoke, sandbox payment, базовый a11y/security review, есть мониторинг, backup/rollback и ответственные за инцидент.

## Открытые QA-зависимости

До финализации набора тестов требуются: правильный NDI `PartyID`, SFTP-доступ и формат/расписание файлов, правила цены/НДС/округления, платёжный провайдер и его authorization/capture возможности, правила самовывоза/доставки, схема Notion, Telegram destination, API-доступ Statens vegvesen и окончательная граница `nb`/`ru`.

Отсутствие этих данных не оправдывает пропуск тестирования: до их получения используются fakes и явно помеченные assumptions. Но оно блокирует production-активацию соответствующей интеграции.
