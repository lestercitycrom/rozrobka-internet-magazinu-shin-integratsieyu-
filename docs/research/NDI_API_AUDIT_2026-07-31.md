# NDI Sales API — первичный технический аудит

Дата проверки: 2026-07-31, обновлено после получения оригинальных вложений NDI  
Исполнитель: Mister Red  
Статус: **условно пригоден как часть интеграции; недостаточен как единственный источник данных**

Секреты и выданные NDI учётные данные в репозиторий не записывались.

## Короткий вывод

NDI Sales API существует, доступен по HTTPS, выданная Basic-аутентификация работает, а WSDL/XSD читаются. Контракт позволяет:

- запросить quote по уже известному артикулу;
- получить доступное количество и дату поставки;
- получить варианты замены;
- разместить заказ;
- получить сведения об отгрузке/заказе.

API не является каталогом. Массовый ассортимент, цены, атрибуты и склад поступают из файловых выгрузок. Отдельные операции резервирования и отмены в опубликованном контракте отсутствуют.

После получения оригинального `A2_Inquiry_Request.xml` обнаружено обязательное пространство имён `xmlns:ew="http://www.reifen.net"`, отсутствовавшее в первом пробном запросе. Повторный read-only Inquiry строго по примеру NDI успешно вернул `quote_A2`, `ErrorCode=0`, доступное количество и дату поставки. Первоначальная ошибка XML была вызвана форматом запроса, а не неисправностью endpoint.

Остаётся настройка учётной записи EasyTire: переданный отдельно тестовый `PartyID` возвращает `ErrorCode=915`, то есть идентификатор покупателя не соответствует аутентифицированной учётной записи. Правильный `PartyID` должен подтвердить NDI.

## Проверенное окружение

- Endpoint: `https://salesapi.ndias.com/EndPoint`
- UAT endpoint из документации: `https://uat-salesapi.ndias.com/EndPoint`
- Test UI: `https://salesapi.ndias.com/servicetest`
- WSDL: `https://salesapi.ndias.com/service.svc?wsdl`
- Версия, показанная тестовым интерфейсом: `2021.6.[21678]`
- Аутентификация: HTTP Basic Authentication
- Формат: XML, EDIWheel/NDI

Выданные EasyTire credentials работают на `salesapi.ndias.com`, но не авторизуются на UAT endpoint. В письме NDI отдельно разрешено временно использовать рабочий endpoint, при этом тестовые заказы должны останавливаться до исполнения.

## Результаты сетевой проверки

| Проверка | Результат |
|---|---|
| Запрос без авторизации | `401 Unauthorized`, Basic realm |
| Запрос с выданными данными | `200 OK` |
| HTTPS/TLS | соединение устанавливается |
| Пять последовательных авторизованных запросов | 5/5 успешных HTTP-ответов |
| Полное время ответа | 0,181–0,225 секунды |
| WSDL | доступен, HTTP 200 |
| Импортированные WSDL/XSD | доступны, HTTP 200 |

Это проверка доступности, а не нагрузочный тест. Лимиты, квоты и допустимая частота вызовов в доступных материалах не указаны.

## Обнаруженные операции

Тестовый endpoint заявляет поддержку:

- `NDIOrder -> NDIResponse`;
- `NDIStatus -> NDIStatusResponse`;
- `inquiry_A2 -> quote_A2`;
- `order_A2 -> order_response_A2`;
- `order -> order_response`.

WSDL содержит:

- `GetQuote` / `GetQuoteAuth`;
- `PlaceOrder` / `PlaceOrderAuth`;
- `GetOrderDespatch` / `GetOrderDespatchAuth`;
- `GetToken`.

Тестовая страница помечает SOAP C1 методы как obsolete. Основной кандидат для новой интеграции — HTTPS endpoint с EDIWheel A2, а не устаревший SOAP-контур.

## Возможности Quote

XSD ответа содержит:

- идентификаторы артикула;
- описание;
- признак доступности;
- доступное количество;
- дату и время поставки;
- опциональные ценовые поля в общей XSD-модели;
- сведения о продавце/поставщике;
- ошибки строки;
- заменяющие товары и их количество/дату/цену.

Фактический успешный `quote_A2` и присланный NDI пример возвращают количество и дату поставки, но не цену. Поэтому до отдельного подтверждения NDI цена должна браться из файловой выгрузки, а Inquiry используется для финальной проверки наличия и срока по уже выбранному SKU.

## Полученные файловые выгрузки

- `Export.xlsx`: шины, 1082 товарные строки, 34 поля, включая `Gross_Price`, `Net_Price`, размеры, сезонность, маркировки и ссылку изображения.
- `Export_1.xlsx`: диски, 502 товарные строки, 14 полей, включая ширину, диаметр, PCD, ET, DIA, цвет и цены.
- `Export_2.xlsx`: остатки, 2304 товарные строки по складам Norway, Vestby, Kristiansand, Trondheim, Tromsø, Bergen и Kopervik.

Это подтверждает рабочую схему: файловая выгрузка формирует локальный каталог и цены, API проверяет доступность/дату и создаёт заказ.

## Выполненные read-only тесты

1. Проверена защита endpoint без авторизации.
2. Проверена выданная авторизация.
3. Получены WSDL, импортированный WSDL и три XSD.
4. Инвентаризированы операции и поля inquiry/quote/order.
5. Первый Inquiry без namespace вернул ошибку XML-десериализации.
6. После получения вложений запрос повторён с обязательным `xmlns:ew="http://www.reifen.net"` и тестовым артикулом NDI.
7. Получен корректный `quote_A2`: `ErrorCode=0`, доступное количество `1`, дата поставки `2026-07-31`.
8. Запрос с тестовым `PartyID` из закрытых материалов дошёл до бизнес-валидации и вернул `ErrorCode=915` — код покупателя не соответствует данным Basic-аутентификации.
9. Проверен UAT endpoint из документации: выданные EasyTire credentials там возвращают `401 Unauthorized`.

Заказ намеренно не отправлялся: `PlaceOrder` меняет внешнее состояние. Даже тестовый контур NDI требует отдельного согласования конкретного артикула, количества и сценария отмены.

## Технические риски

### 1. Требуется правильный PartyID EasyTire

Транспорт, авторизация и Inquiry работают. Для запросов от лица EasyTire NDI должен подтвердить идентификатор покупателя, связанный с выданным API-логином.

### 2. Устаревший SOAP-контур

WSDL рекламирует адрес по обычному HTTP, тестовая страница помечает SOAP-методы obsolete, а POST на `Service.svc` по HTTPS не дал рабочего SOAP-ответа. Передавать Basic credentials по HTTP нельзя.

### 3. Нет резерва и отмены

Обычный безопасный поток `quote -> reserve -> payment -> confirm` этим контрактом не подтверждён.

Предпочтительный вариант, если платёжный провайдер поддерживает authorization/capture:

```text
NDI Quote
  -> авторизация суммы без списания
  -> PlaceOrder NDI
  -> capture при подтверждённом заказе
  -> void при отказе NDI
```

Если authorization/capture недоступен, потребуется политика ручной обработки и возврата при расхождении остатка.

### 4. Суточная файловая выгрузка

Каталог может быть устаревшим между выгрузками. Перед оплатой Inquiry обязателен.

### 5. Неизвестные лимиты и SLA

Нет подтверждённых rate limits, SLA, окна обслуживания, политики повторов и контактной процедуры при сбое.

## Что требуется для завершения аудита

От заказчика/NDI всё ещё нужны:

1. SFTP host, порт, логин и способ аутентификации.
2. Правильный `PartyID` EasyTire, связанный с API-логином.
3. Подтверждение, возвращает ли NDI актуальную цену через какой-либо Inquiry-вариант, либо цена обновляется только файлами.
4. Письменное подтверждение, что заказ через текущий рабочий endpoint будет остановлен и может быть безопасно создан.
5. Инструкция или метод отмены тестового заказа.
6. Ответ NDI по резервированию, отмене, лимитам и SLA.

## Решение для проекта

Статус интеграции: **жёлтый, но техническая жизнеспособность Inquiry подтверждена**.

- Для архитектуры `CSV/SFTP -> локальный каталог -> Inquiry перед checkout -> Order` API подходит концептуально.
- Для полного магазина только NDI API недостаточно.
- Можно начинать проектирование импорта каталога по полученным Excel-примерам.
- Начинать автоматическое создание заказа без правильного PartyID и согласованного тестового заказа нельзя.
- Headless-автоматизация дилерского кабинета сейчас не требуется и должна оставаться только аварийным вариантом.
