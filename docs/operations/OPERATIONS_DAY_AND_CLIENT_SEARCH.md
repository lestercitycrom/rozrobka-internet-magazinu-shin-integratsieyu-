# Рабочий день и поиск клиентов

Обновлено: 2026-09-15
Область: GitHub Issue #66

## Для сотрудника

1. Откройте прямой пункт `Админка → Рабочий день`.
2. По умолчанию открывается сегодня в `Europe/Oslo`. Выберите дату и ресурс быстрыми ссылками или фильтром: все задачи, мастерская, выездная машина 1/2 либо выезды без назначенной машины. Ссылка «Заявки без даты» открывает отдельную очередь.
3. Подтверждённые слоты и желаемые периоды идут по времени; задачи без структурированного времени находятся после них и явно помечены как неподтверждённые.
4. Блок подготовки строится только из строк текущих даты и ресурса, отдельно показывает подтверждённые и ожидающие подтверждения задачи и перечисляет действия по каждому автомобилю. Для `RENEW` и `LAST` без номера комплекта сотрудник увидит «Уточнить номер перед подготовкой».
5. Закрытые и отменённые заявки скрыты по умолчанию. Галочка истории показывает оба статуса, но никогда не превращает их в действия подготовки.
6. В карточке видны телефон, адрес, район, все автомобили, госномера, номера комплектов Dekkhotell и операция подготовки. Ссылка на Google Maps выполняет обычный поиск по введённой строке адреса и не является проверенным географическим pin.
7. Переход в полную заявку и редактирование сохраняют текущие дату, ресурс и режим истории. После ошибки проверки или успешного сохранения кнопка возврата ведёт к тому же рабочему дню; внешние адреса возврата не принимаются. Связанный клиент и контактный снимок заявки при таком переходе не перезаписываются автоматически.

В рабочем дне нет автоматического маршрута, распределения машин, складского остатка, изменения времени или финансовых действий. Это оперативное представление уже существующих заявок.

## Полный поиск клиента

В форме заявки клиент больше не загружается из ограниченного списка первых 250 записей. Поле поиска обращается к серверу страницами по 20 результатов и ищет по:

- имени;
- нормализованному телефону;
- e-mail;
- госномеру в явно связанной заявке, включая второй и последующие автомобили; регистр букв не влияет на поиск в SQLite и MySQL.

Выбор меняет только явную связь `client_id`. Контактный снимок заявки не переписывается, автоматического объединения клиентов или назначения владельца автомобиля нет. Госномер в истории означает только то, что он был сохранён в связанной заявке; это не подтверждение текущего владельца.

Ответ lookup содержит только `id` и подпись `имя · телефон`, закрыт от кэширования и доступен только ролям Owner и Operations. Editor, Customer, неактивный пользователь и гость не получают этот доступ.

## Проверка

- Feature: полный поиск, 1001 синтетический клиент, стабильная пагинация, RBAC, отсутствие утечки внутренних полей, номера второго/третьего автомобиля, отрицательные совпадения по несвязанным заявкам и служебным JSON-полям, рабочий день/дата/ресурс/хронология/история/возврат.
- MySQL CI regression: смешанный регистр верхнего и JSON-госномера (включая второй/третий автомобиль), только явно связанные заявки, отрицательные случаи для номера хранения и несвязанных заявок.
- Playwright: реальный выбор и сохранение клиента за пределами прежних 250, полный операторский переход с возвратом, NB/RU, подтверждённая и ожидающая подготовка, история без действий, пять автомобилей, LAST и текстовый номер `00042-A`, ширины 1440/390/320 без горизонтального скролла страницы.
- Внешние API, платежи, Telegram, Notion, письма и реальные клиентские данные в этих сценариях не используются.

## Откат

Изменений схемы базы данных в Issue #66 нет. Откат — возврат к предыдущему приложению; данные клиентов и заявок не удаляются.
